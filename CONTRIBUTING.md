# Contributing to Dockit

Thanks for your interest in improving Dockit! This guide covers how to set up the project, make a change, and get it merged.

## Ways to contribute

- **Report a bug** or **request a feature** using the [issue templates](https://github.com/Amanbig/dockit/issues/new/choose).
- **Improve the docs**: typos, unclear steps, and missing examples all count.
- **Fix an issue**: check [`good first issue`](https://github.com/Amanbig/dockit/labels/good%20first%20issue) and [`help wanted`](https://github.com/Amanbig/dockit/labels/help%20wanted).
- **Test on your setup**: Podman, Windows named pipes, macOS with Colima or Docker Desktop, and other less common combinations are especially valuable.

For anything larger than a small fix, please open an issue first so we can agree on the approach before you spend time on it.

## Development setup

You need:

- Go (see `go.mod`) and Node.js 20+
- The [Wails CLI](https://wails.io/docs/gettingstarted/installation) v2.9+
- Docker or Podman, to try your changes against a real engine
- **Linux only**: GTK and WebKit headers, see the [README](README.md#getting-started)

```bash
git clone https://github.com/<your-username>/dockit.git
cd dockit
(cd frontend && npm install)
wails dev -tags webkit2_41      # drop "-tags webkit2_41" on Windows/macOS or older WebKitGTK
```

`wails dev` hot-reloads the frontend and rebuilds the Go backend on change.

## Making a change

1. Fork the repo and create a branch from `main`: `git checkout -b fix/short-description`.
2. Make your change. Keep it focused; unrelated cleanups belong in a separate PR.
3. Run the checks:

   ```bash
   gofmt -l .                     # should print nothing
   go vet ./internal/...
   go test ./internal/...
   cd frontend && npm run build
   ```

4. Try the change in the running app (`wails dev`). For UI changes, check both light and dark themes, and test with Docker *and* Podman if the change touches the engine layer.
5. Open a pull request against `main` and fill in the template.

## Project conventions

- **Go**: format with `gofmt`. Domain logic lives in `internal/<domain>`; methods exposed to the UI are bound in `app.go`. Go through the `internal/runtime` abstraction rather than calling Docker or Podman directly, so both engines keep working.
- **Frontend**: React function components and Tailwind CSS v4, in `frontend/src/components`. Use the in-app confirm dialogs and toasts instead of native `confirm`/`alert`.
- **Generated code**: `frontend/wailsjs/` is generated by Wails. After changing exported methods or types in Go, run `wails dev` or `wails generate module` and commit the result.
- **Host commands**: anything that runs shell commands (terminal, Compose, installer) must avoid string-built commands from user input, and keep the existing timeouts and process-group cleanup.
- **Secrets**: never log registry credentials or `.env` contents.
- **Tests**: add tests for new backend logic where practical (see `internal/compose/manager_test.go`).

## Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(compose): add --rmi option to the Down dialog
fix(terminal): kill the whole process group on cancel
docs: clarify Podman socket detection
```

Common types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `chore`, `ci`.

## Pull request checklist

- [ ] The change is focused and the PR description explains *why*
- [ ] `gofmt`, `go vet`, `go test`, and `npm run build` pass
- [ ] Tested manually, with notes or screenshots for UI changes
- [ ] Docs and `RELEASE_NOTES.md` updated if user-visible behavior changed

A maintainer will review as soon as possible. Small, focused PRs get merged fastest.

## Releases

Maintainers bump versions with `./scripts/bump-version.sh <patch|minor|major|x.y.z> [--tag]`, which keeps `internal/version/version.go`, `wails.json`, and `frontend/package.json` in sync. Pushing a `v*` tag triggers the [release workflow](.github/workflows/release.yml).
